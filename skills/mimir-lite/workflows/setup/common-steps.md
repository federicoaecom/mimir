# Setup common steps

Part of the [setup workflow](../setup.md). This file holds WORKFLOW steps 9 to 34. Read it in every mode after step 8. The earlier WORKFLOW steps (WORKFLOW step 0, the catalog reminder, through the CREATION BLOCK) and the sections named in capitals are in [`setup.md`](../setup.md), except steps 8.a to 8.h in [`update.md`](update.md), the fast-path precondition and the correction plan in [`audit.md`](audit.md), EXPECTED LOCAL WRAPPERS in [`wrappers.md`](wrappers.md), and CONSTRAINTS in [`constraints.md`](constraints.md). Relative paths resolve from the `setup/` folder (see PATH RESOLUTION in `setup.md`).

9. Validate the setup structure: `scripts`, `Temp`, `IdeXpzExports`, `KbObjectsXml`, and `KbIntelligence` when adopted (the scaffolder creates all five).
10. The scaffolder writes the root `.gitignore` and the `.gitkeep` files. When building by hand, create the `.gitignore` when the workspace is Git-versioned or the user accepts preparing for future versioning: cover `Temp/*`, `KbIntelligence/kb-intelligence.sqlite`, `KbIntelligence/kb-intelligence-validation.json`, and `IdeXpzExports/*`; create the matching `.gitkeep` in each `folder/*`-covered folder in the same step; never reference a `.gitkeep` you did not create; never ignore `KbObjectsXml`.
11. If not yet Git-versioned, the agent may offer to initialize local Git versioning; never run `git init` without explicit approval.
12. If the user accepts and Git is not functional locally, offer to install or guide the install first.
13. If `kb-source-metadata.md` does not exist, create it with the nominal `last_xpz_materialization_run_at` field, matching the shared engine's format (the scaffolder does this). Once the native KB folder is confirmed, run `Resolve-*KbIdentity.ps1 -UpdateMetadata` (engine `Resolve-GeneXusKbIdentity.ps1`) to fill the stable-identity fields; if resolution blocks, create at most partial metadata and declare the stable-identity fields pending. In an XPZ-only workspace, the first sync fills them instead (see [XPZ-only workspace](../setup.md#xpz-only-workspace)). If `kb-source-metadata.md` already exists, do not touch fields outside the current authority — use the approved identity-reconciliation workstream via `Update-MimirKbSourceMetadataIdentity.ps1` for missing/divergent fields, preserving real operational timestamps the freshness gate depends on.
14. External memory: follow the core rule in [`SKILL.md`](../../SKILL.md#core-rules-apply-to-every-workflow) on saving anything to a memory tool outside the workspace (ask first, naming what and where). The workspace's own `AGENTS.md` and `README.md` are the memory layer for setup.
15. Explain each folder's role (per RESPONSIBILITIES in [`setup.md`](../setup.md)).
16. If `KbObjectsXml` does not exist yet, treat the corpus as not yet materialized.
17. Setup does not create generated-object workstreams or import-package folders; those activities are outside Mimir Lite's supported workflow.
18. If `IdeXpzExports` is missing and the flow depends on `XPZ`, ask for the intended path or create the default folder when repository policy allows.
19. If `scripts` exists with no minimum local wrappers, rerun the scaffolder per the "Wrapper bootstrap when `scripts` has none" list in RESPONSIBILITIES ([`setup.md`](../setup.md)).
20. If the agent tool in use has a command allowlist or equivalent permission configuration, then whenever a local `.ps1` wrapper expected by the shared base is created or confirmed — any mandatory or adopted recommended wrapper — offer to register the matching allow rule in that configuration. Ask before writing, as in 20a: show the settings file's full path and the exact rule or rules, verbatim, on screen with the question, as COMMUNICATION, **Show before asking** (in [`setup.md`](../setup.md)) describes, and write only after an explicit yes. One question may cover this rule and the 20a rules when it shows each verbatim; approving a plan or another question is not approval of this write. This covers the core gates/readers (`Test-*KbIndexGate.ps1`, `Get-*KbMetadata.ps1`, `Test-*KbMetadataWrapper.ps1`, `Test-*KbStructure.ps1`), materialization wrappers, and the identity resolver. Register each script by its real local name (not the sanitized example name), or with one rule scoped to the workspace's `scripts` folder when the tool's rules support a path prefix, always with an absolute, literal path matching the canonical command form (see [Running scripts](../../SKILL.md#running-scripts) in `SKILL.md`). Treat this as part of bootstrap/update, not a manual follow-up — ask it before declaring the completion state. For a tool with no allowlist, this step is not applicable: it must not block any completion state, and the user handles any prompt through that tool's own permission flow.

    Tool note: Claude Code. One rule scoped to the workspace's `scripts` folder covers every wrapper run with the canonical command form: add `Bash(pwsh -NoProfile -File "<KbWorkspace>/scripts/*)` to `permissions.allow` in the workspace's `.claude/settings.json` (e.g. `Bash(pwsh -NoProfile -File "C:/KBs/SampleKbWorkspace/scripts/*)`). Claude Code matches the text before the `*` literally, so the rule only covers commands spelled exactly in the canonical form (literal absolute path, forward slashes, double quotes); never write `..` in a command path, since the rule would still match it. When the user has enabled Claude Code's PowerShell tool, add the same rule with the `PowerShell(...)` prefix: `PowerShell(pwsh -NoProfile -File "<KbWorkspace>/scripts/*)`. Create the file with a minimal structure if it does not exist; if it does, read current entries and insert only the missing ones. These project settings apply only to a session started in the KB workspace folder, so the closing message tells the user to start the agent tool there for KB work. Rule syntax: <https://code.claude.com/docs/en/permissions>.

20a. Some steps call a shared script directly, with no local wrapper: the catalog reminder (WORKFLOW step 0 in [`setup.md`](../setup.md), when it runs), the sync pre-scan `Get-GeneXusXpzObjectInventory.ps1` (**sync** workflow step 7b), and any direct engine call that passes `-RepoRoot` to resolve the workspace's own folders. When the agent tool in use has a command allowlist, check that it has an entry covering the shared base's `scripts` folder, using an absolute, literal path — never a placeholder. If missing, offer to add it right after the scaffolder (8.s.5 in [`setup.md`](../setup.md)), before the first of these calls, and wait for explicit approval. The scaffolder (`<mimir-lite-root>/skills/mimir-lite/scripts/New-MimirKbWorkspace.ps1`, 8.s.2) is also a direct shared-script call, and this rule would match it, but it runs once before this question by design: it creates the workspace whose settings file holds the allow rules, and those rules apply only to a session started in the workspace folder, so writing the rule first would not spare the scaffolder's permission prompt. Treat this as bootstrap when a direct engine call is needed for an approved read, sync, index, or identity workflow, or as an update when the direct engine call is new to this folder. When the agent tool also has file-read permission rules, check in the same way for a read rule covering the clone's `skills` folder (`<mimir-lite-root>/skills`, both skills): the agent reads the skill's own workflow and reference files there, outside the KB workspace folder, so a session with default permissions asks approval for each read. Also check for one read rule for each skill link that exists in the tool's own skills folder (`mimir-lite`, and `mimir-delegate` when it is linked there): the agent reads the skill through its link path, and the tool matches the path as requested without resolving the link, so the clone-path rule alone does not cover those reads (seen in an end-to-end run). Keep the clone-path rule for reads through `<mimir-lite-root>`. Offer the read rules in the same question as the shared-scripts rule, shown verbatim (COMMUNICATION, **Show before asking**, in [`setup.md`](../setup.md)), write them only after an explicit yes, and insert each rule only when it is missing: never remove or overwrite an existing entry (see also 8.e in [`update.md`](update.md)). Write all of these rules only to the KB workspace's settings, never to user-level settings. For a tool with no allowlist, this step is not applicable.

    Tool note: Claude Code. The entry is `Bash(pwsh -NoProfile -File "<mimir-lite-root>/skills/mimir-lite/scripts/*)` in `.claude/settings.json` (e.g. `Bash(pwsh -NoProfile -File "C:/Tools/mimir-lite/skills/mimir-lite/scripts/*)`), plus the same rule with the `PowerShell(...)` prefix when the PowerShell tool is enabled; create the file with that entry if it does not exist. The read rules go in the same `permissions.allow` list. The clone-path rule is `Read(//<root>/skills/**)`, where `//` starts an absolute path from the filesystem root and `<root>` is `<mimir-lite-root>` in POSIX form without its leading slash. On Windows, Claude Code normalizes `C:\Tools\mimir-lite` to `/c/Tools/mimir-lite` (lowercase drive letter, forward slashes), so a clone there gives `Read(//c/Tools/mimir-lite/skills/**)`; on Linux or macOS, a clone at `/home/user/mimir-lite` gives `Read(//home/user/mimir-lite/skills/**)`. A single leading `/` is relative to the session's primary working directory (the KB workspace, for a session started there), not absolute. For the skill links under `~/.claude/skills`, add `Read(~/.claude/skills/mimir-lite/**)`, and `Read(~/.claude/skills/mimir-delegate/**)` when that link exists; `~/` is Claude Code's documented home-relative form, so these two rules need no literal path. When the skill is installed for this project only (the **install** workflow's scope), its links sit inside the KB workspace: use the project-relative `Read(/.claude/skills/mimir-lite/**)` (and `Read(/.claude/skills/mimir-delegate/**)` when that link exists) instead of the `~/` rules. Claude Code also applies `Read` rules, best effort, to Grep and Glob. Do not offer `permissions.additionalDirectories` instead: it opens the whole clone, and in `acceptEdits` mode it auto-approves edits there.

21. If `KbIntelligence` is missing, guide creating it as the derived-artifact folder before installing index wrappers.
22. If `KbObjectsXml` has no materialized snapshot yet, do not attempt to generate `kb-intelligence.sqlite` — only prepare the folder and local wrappers.

25. Before declaring setup complete, validate that the minimum local-wrapper layer in `scripts` exists for the workspace's adopted official flow.
26. When local wrappers are derived from `.example.ps1` files, validate they keep no sanitized placeholders in effective configuration before classifying them as existing minimum wrappers. The scaffolder resolves the shared-root placeholder always and the native-KB placeholder when `-KbNativePath` is given (to an empty value with `-XpzOnly`); its `PENDING` lines name what is left.
27. Mimir Lite setup prepares the read, sync, index, and identity workspace only; it does not generate, import, build, or deploy GeneXus objects.

28. If the folder/document structure is ready but the minimum local-wrapper layer is missing or still holds sanitized placeholders in effective configuration, report this as "partial structure"/"incomplete bootstrap" — never as setup complete.
29. On concluding initial setup, state explicitly that the structure is ready but `KbObjectsXml` has not been materialized yet, and that the structure gate and the index gate pass only after the first sync builds the index.
30. If the first official materialization happens after setup, update or clear the provisional local memory from setup that still says "not materialized"/"waiting for the first XPZ" or equivalent.
31. On concluding initial setup, explain that the supported next action is exporting an XPZ from the GeneXus IDE and using the **sync** workflow, with the agent tool started in the KB workspace folder so the allow rules written there apply (step 20). When this session was not opened in the KB workspace folder, say that permission prompts continue in this session and that the allow rules apply once the agent tool is reopened in `<KbWorkspace>` (skip the part about prompts when this session runs without permission prompts, for example in a bypass or auto-approve mode); only when the session was opened in that folder, say that the scripts now run without prompts.
32. On closing initial setup, recommend the **install** workflow by name, in a sentence of its own, for a full ecosystem audit beyond what this workflow itself checks. When the install audit already ran in this session, say so, give its result, and recommend running the **install** workflow again after every `git pull` of the shared checkout.
33. Do not propose MSBuild-based export or local object-generation alternatives; the supported input is a user-exported XPZ from the GeneXus IDE, consumed by the **sync** workflow.
34. **Setup-audit metadata write.** On declaring any successful canonical completion state (`ready_for_first_materialization`, `materialized_and_index_validated`, or `wrappers_updated`), write `last_setup_audit_run_at` with the successful audit's timestamp and `setup_contract_signature_version`/`setup_contract_signature_hash` with the current setup contract signature, in `kb-source-metadata.md`'s frontmatter; never write them for `bootstrap_incomplete` or `methodology_update_pending`. The timestamp must be ISO 8601 with a timezone offset, matching `last_xpz_materialization_run_at`'s format. Prefer `Set-*KbSetupAuditTimestamp.ps1` (engine `../../scripts/Set-MimirSetupAuditTimestamp.ps1`), which updates only these fields and preserves the rest of the file; manual editing only when the wrapper is missing and the approved workstream allows local writes. These fields record a successful setup audit; they never substitute for or mirror `last_xpz_materialization_run_at`/`last_index_build_run_at`. The precondition's `setup_ready_metadata_pending` sub-state (in [`audit.md`](audit.md)) uses this same write once the full audit just passed with a compatible successful canonical state — never default-deferred to another session. This write is the last write of the setup run: make every edit to `AGENTS.md`, `README.md`, and other workspace files first, then run the setup audit, then write the timestamp; when a workspace file changes after the timestamp, rerun the audit and this write.
