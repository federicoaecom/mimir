# Changelog

All notable changes to Mimir Lite are documented in this file.

The format follows [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/), and the project uses [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- The KB index extracts relations from classic GeneXus exports (GeneXus 7.5 to 9, root `dataSource="gx-legacy-export"`), so `who-uses`, `what-uses`, and `impact-basic` answer for GeneXus 8 and 9 objects, which were inventoried without relations before. A classic `Report` is indexed and queried as its own type `Report` instead of being skipped as a legacy orphan (registry flag `indexedByKbIntelligence`; classic identity is type + name, so a `Report` and a `Procedure` with the same name stay distinct). Classic calls are read from every `<Rules>` and `<Events>` body and every `<Source>` inside a `<CodeBlock>` (comments skipped; a `<Source>` elsewhere, such as the HTML of a `WebPanel` `HTMLForm` or of the `Documentation`, or a `Report` print control, is not read) by an extractor of their own that strips the object-type prefix of `call(`, `udp(`, and `link(`: `P` → `calls_procedure`, `R` → `calls_report`, `T` → `calls_transaction`, `W` → `calls_workpanel` (rules `classic_call_command`, `classic_udp_func`, `classic_link`); a call through a variable or with another prefix gives no relation, and the modern call forms no longer read classic code (the modern `call(PAGO)` would match a `Procedure` named `PAGO` instead of `AGO`). Attribute references (`code_references_attribute`, rule `code_attribute_reference`) come from the same sections, read like the matching modern Part: `Report Source` and `Procedure Source`, `Rules` (with `Rules write` for Transaction assignment rules), and `Events`, each with read and write roles. Reverse-relation coverage for an `Attribute` target lists `Report` as partly extracted (extracted: Source reads, rule reads, block writes; missing: ambiguous writes, layout, Business Component members). Not covered: a Web Panel call prefix (none observed), a `WorkPanel` as a call source or queried object, the table a classic `for each` navigates, and `.xpw` exports (GeneXus 7.0 and earlier). The extractor version goes from 18 to 19, so the index gate reports existing indexes as built by an older extractor until they are rebuilt once. The KB index reference and the README follow.

### Changed

- README: the GeneXus versions table lists GeneXus X and X Evolution 1 as tested with public samples: 21 small public exports (export header 3.1, builds 13780 to 27264 or no build, dated 2007 to 2010) sync, index, and produce relations. The files do not name the product version, so the two are not told apart, and no full agent run was made.

### Fixed

- The sync reads GeneXus 8 classic exports: the `<WebPanel>` element is registered as the modern `WebPanel` type, and the blank-name `<Group>` each package carries for its ungrouped subtypes is split into one `SubTypeGroup/<subtype>.xml` per subtype, so a later package with fewer subtypes never overwrites the others; a blank `Group` without a `Subtype`, an unnamed ungrouped `Subtype`, and two `Group` items with the same name in one package fail closed. A public GeneXus 8.0 export failed before with "name not found in Info/Name for element 'Group'". The README, the sync workflow, and the legacy element registry document GeneXus 8 support.
- The README agent steps (English and Spanish) and the **install** workflow name where the commit after an update comes from: the `Updating <old>..<new>` line of the `pull --ff-only` output (`Already up to date` means it did not change), so reporting it needs no extra command and no extra permission approval.

## [0.7.0] - 2026-10-11

### Added

- `who-uses` on an `Attribute` attaches to each `has_level_attribute` row from a Transaction a `writability` object: that Transaction's materialized writability classification of the attribute (the fields of a `transaction-writable-attributes` row except the file-backed `isFormula` and `formulaExpression`), or `null` when the Transaction has no materialized row; the `text` output adds one `writability:` line to those rows, and the `dependents` of `impact-basic` carry the same field. A foreign key such as `extended-fk-key` is then direct evidence in the answer instead of an inference from the level structure. Existing fields, row order, limits, and the `coverage` object are unchanged, `who-uses` still reads the index alone, and neither the index schema nor the extractor version changes. The KB index reference and the find workflow follow.
- The KB index extracts attribute references from mobile `WorkWith` (WorkWith for Smart Devices) pattern instances: `workwith_references_attribute` (rule `workwith_sd_attribute_reference`) links a `WorkWith` to each inventory attribute named by a `<data attribute="...">` in its list and detail layouts (variables skipped), by its `<orders>`, `<search>`, and `<breakBy>` blocks, and by its advanced `<filterAttribute attribute="...">` filters, in the X Evolution 2 layout and in the `gridData` layout of X Evolution 3, GeneXus 15, and GeneXus 16. One row per object, attribute, and role (`WorkWith layout attribute`, `WorkWith order attribute`, `WorkWith search attribute`, `WorkWith break by attribute`, `WorkWith filter attribute`); a `WorkWithForWeb` with the same name keeps its own rows. Reverse-relation coverage for an `Attribute` target lists `WorkWith` as partly extracted (extracted: layouts, orders, search, break by, filters; missing: grid conditions, rules, events, captions) instead of not extracted, and `WorkWith` stays an unextracted call source. The extractor version goes from 17 to 18, so the index gate reports existing indexes as built by an older extractor until they are rebuilt once. The KB index reference, the find workflow, and the backlog follow.

### Changed

- The **setup** workflow is split so each file reads in one call: `setup.md` keeps the entry, the checklist, and the creation flow, and points to five files under `workflows/setup/`: `audit.md` (the fast-path precondition and the post-audit correction plan), `update.md` (the update block, update mode only), `common-steps.md` (steps 9 to 34, every mode), `wrappers.md` (the expected local wrappers), and `constraints.md` (the constraints, read before any write). The text moved verbatim; step numbers are unchanged. The setup contract manifest lists the five files, so the setup contract signature changes and KB workspaces re-audit once.

### Fixed

- The README agent steps (English and Spanish) and the **install** workflow, from a tenth end-to-end run: when the agent tool has a question prompt with options, the existing-clone report (clean state, current commit, `origin` match) goes into the update question text itself, since text printed right before the call can be skipped; the options stay and the question never becomes free text. The commit is given as its short hash, before and after an update, without a release label: the version the README or the CHANGELOG names is the latest release, not necessarily that commit.
- The **setup** workflow pointer to `setup/wrappers.md` (in `setup.md` and in that file's own introduction), from the same run: in creation mode the scaffolder creates the wrappers and the setup audit checks them (`wrappers/inventory`), so the file is read only when that audit reports a wrapper problem, or when a wrapper is checked, fixed, or created by hand.

## [0.6.0] - 2026-10-10

### Added

- The setup workflow (step 20a) also offers a Claude Code read rule for the clone's `skills` folder, `Read(//<root>/skills/**)` with the clone's absolute path in POSIX form (a clone at `C:\Tools\mimir-lite` gives `Read(//c/Tools/mimir-lite/skills/**)`), so a session with default permissions reads the skill's own workflow and reference files without an approval each time. Because the agent reads the skill through its Claude Code skill link and Claude Code matches that path without resolving the link, setup also offers one read rule for each skill link under `~/.claude/skills`: `Read(~/.claude/skills/mimir-lite/**)`, and `Read(~/.claude/skills/mimir-delegate/**)` when that skill is linked there. The read rules are asked in the same question as the shared-scripts rule, shown verbatim, written to the KB workspace's `.claude/settings.json` only after an explicit yes and each only when missing, and never to user-level settings; `permissions.additionalDirectories` is not offered, since it opens the whole clone. The completion checklist, the scaffolder follow-up order, the README, and the backlog follow. The setup contract signature changes, so every existing KB workspace reports a one-time setup re-audit.

### Changed

- The KB index gives the `write` role (`Rules write`) to the attributes the Transaction rules `Default` and `Equal` assign (their first argument) and to the two a `Serial` rule assigns (its first and second arguments), when the argument is a bare attribute name and the rule starts the Rules Part or follows `;`, `{`, or `}` (the braces of a platform section such as `[web] { noaccept(Attribute); }`); the rule name matches in any case and may carry a trailing `if`, `on`, or `level` clause. Extractor 16 read them as `Rules read`. A Transaction assignment rule `Attribute = expression;` that follows `{` or `}` is now also a `Rules write`; extractor 16 recognized it only at the start of the Rules Part or after `;`. The value expression of the rule and its condition stay reads, `parm(in:Attribute)` stays a read, and the Rules of a `Procedure`, `WebPanel`, or `DataProvider` are unchanged; a write occurrence still gives no read row of its own. The extractor version goes from 16 to 17, so the index gate reports existing indexes as built by an older extractor until they are rebuilt once. The KB index reference and the backlog follow.

### Fixed

- The setup workflow shows the settings file path and every allow and read rule, and the global instruction file path and its exact block, on screen with the question; a rule or block that appears only in a tool input, a permission prompt, or the agent's reasoning was not shown. The README (English and Spanish) and the **install** workflow make the existing-clone report (clean state, current commit, `origin` match) visible text that precedes the update question, never only tool output or reasoning. Both rules keep the agent tool's question prompt with options when it has one, and no question becomes free text; when the prompt can show a text block with an option (Claude Code's option `preview`), the setup puts the file path and the exact text there, in every option that approves a write.

## [0.5.0] - 2026-10-10

### Added

- The KB index extracts attribute references from `WorkWithForWeb` pattern instances: a new relation `workwith_references_attribute` links a web Work With to each attribute its grids, orders, view tabs, and fixed data name (`<attribute attribute="<typeGuid>-<Name>">`), its description attribute, its filter attributes (`<filterAttribute name="<Name>">`), and the attribute names of its filter conditions (`<condition value="...">` in the selection and Grid tab filters, `evidence_role` `WorkWithForWeb condition`), so `who-uses` on an `Attribute` now lists those Work With objects. A condition is tokenized after XML unescaping: string literals, `//` comments, `&variables`, members after `.`, called objects, and keywords such as `like`, `when`, `not`, and `null` are skipped, while call arguments and attributes with a method count. Targets resolve only against the Attribute inventory, each object and attribute pair yields one relation (the first occurrence in document order is the evidence), and `<variable>` elements are not read; the mobile `WorkWith` is not a source.
- The KB index extracts attribute reads and writes from GeneXus code: a new relation `code_references_attribute` (rule `code_attribute_reference`) links a `Procedure`, `WebPanel`, `Transaction`, or `DataProvider` to each attribute its code names, read only from the code Parts selected by Part type (Procedure Source, the Rules and Events of Procedure, WebPanel, and Transaction, and the Source and Rules of DataProvider), so `who-uses` on an `Attribute` now lists that code. `evidence_role` names the Part with the `read` or `write` role (`Procedure Source read`, `Rules read`, `Events read`, `DataProvider Source read`, and the same with `write`); each object, attribute, and role yields one relation at its first occurrence, and a write occurrence gives no read row of its own. The `write` role marks only unambiguous assignment targets: `Attribute = expression` at a statement start inside a `for each` ... `endfor` or `new` ... `endnew` block (keywords in any case, nested blocks, inside `if` and `do case`; not in the innermost block's `when none` or `when duplicate` branch, nor in a plain `for` loop alone), a Transaction assignment rule `Attribute = expression [if condition];`, and an item's left side in a DataProvider whose output is a Transaction; a top-level assignment in an Event or Procedure, `=` in conditions, and `parm(in:Attribute)` stay reads. A small tokenizer skips `//` and `/* */` comments, string literals, `&variables` and their members, members after `.`, called objects, the table after `for each`, Domain enumeration values (`CompanyType.Startup`), `Event` header lines, the `Load` and `Refresh` commands alone on their line, and keywords; a name is a called object only when `(` follows on the same line; call arguments, method receivers, and the attributes after `where`, `order`, and `defined by` count. DataProvider group headers are skipped, and an item's left side counts only when the DataProvider's output is a Transaction (with an SDT output it names an SDT item). WebForm, Layout, and Conditions Parts, and a bare `<Source>` outside any `<Part>`, are not read by this extractor; the other extractors are unchanged. The extractor version goes from 12 to 16 (the `WorkWithForWeb` references above, these code reads and writes, and the comment and filter fixes under Fixed), so the index gate reports existing indexes as built by an older extractor until they are rebuilt once.
- Reverse-relation coverage for an `Attribute` target gains `partially_extracted_source_types`: `WorkWithForWeb` moves there from `unextracted_source_types`, with its count, `extracted: ["grids", "filters", "orders", "views", "filter conditions"]`, and `missing: ["captions", "parameters", "tab conditions", "code"]`, since its grid, filter, order, view, and filter condition references are now indexed but its view captions, view and action parameters, tab conditions, and code are not. The claim follows the index's `extractor_signature_version`: an index built by extractor 13 reports `filter conditions` as missing, and an older index, or one without a numeric version, keeps `WorkWithForWeb` under `unextracted_source_types`. `complete` stays `false` while any unextracted or partly extracted type has objects in the index, and the `text` line adds `attribute uses are partly extracted from WorkWithForWeb (N): grids, filters, orders, views and filter conditions are indexed, captions, parameters, tab conditions and code are not`. The list is always empty for the `calls` scope. The field is additive; `scope`, exit codes, and the index schema are unchanged. The find workflow, the KB index reference, the README limits, and the backlog follow.
- Reverse-relation coverage for an `Attribute` target lists `Procedure`, `WebPanel`, `Transaction`, and `DataProvider` under `partially_extracted_source_types` on an index built by extractor 15, with the code reads and writes it holds and what it misses: `Procedure` `extracted: ["Source reads", "rule reads", "block writes"]`, `missing: ["ambiguous writes", "conditions", "layout", "Business Component members", "code outside a Part"]`; `WebPanel` `extracted: ["rule reads", "event reads", "block writes"]`, `missing: ["ambiguous writes", "conditions", "WebForm bindings", "Business Component members", "code outside a Part"]`; `Transaction` `extracted: ["rule reads", "rule writes", "event reads", "block writes"]`, `missing: ["ambiguous writes", "WebForm bindings", "Business Component members", "code outside a Part"]`; `DataProvider` `extracted: ["Source reads", "rule reads", "Transaction item writes"]`, `missing: ["SDT output items", "Business Component members", "code outside a Part"]`. `code outside a Part` names a `<Source>` not inside a `<Part>`, which the code extractor does not read. An older index keeps them under `unextracted_source_types`. The find workflow, the KB index reference, the README limits, the glossary, and the backlog follow.

### Fixed

- The KB index no longer cuts a line of code at a `//` inside a string literal: a call after `'http://...'`, `"a // b"`, or `!"..."` on the same line of a `Source` is now found, while a `//` outside a literal still starts a comment and a whole commented line is still skipped. A quote inside a `/* ... */` block comment on the same line no longer opens a literal, so a `//` after it still starts a comment, and code after a closed block comment is still read.
- The `WorkWith` and `WorkWithForWeb` condition-to-`Procedure` relations (`workwith_condition_calls_procedure`, `workwith_condition_attribute_calls_procedure`) read every line of a multi-line condition: a `//` comment ends at its own line instead of dropping the rest of the value, and a `//` inside a string literal is not a comment.
- `WorkWithForWeb` filter conditions: a quoted `>` or `/>` in a `<filter>` tag attribute no longer ends the tag early, so the filter's conditions are read and a `<condition>` after a self-closing filter is not taken as a filter condition.

## [0.4.0] - 2026-10-09

### Added

- The install audit (`Test-MimirSkillsRegistration.ps1`) accepts `-OnlyTool <names>`, the complement of `-SkipTool`: every built-in tool not listed is reported `skipped_by_choice`, exactly as if passed to `-SkipTool`, so the audit runs once with the right choices declared. It takes a comma-separated list like `-SkipTool`; an unknown name, or combining it with `-SkipTool`, stops with `BLOCK:`, exit `1`, and nothing on stdout. `-SkipSkill` still combines with it, and every `-AdditionalSkillsRoot` entry stays audited. The README agent steps and the install workflow map each skills folder the user approved to its tools (`~/.claude/skills` to `ClaudeCode`; `~/.agents/skills` to `Codex`, `OpenCode`, and `Antigravity`; `~/.cursor/skills` to `Cursor`; `~/.gemini/config/skills` to `Antigravity`), run the audit once with `-OnlyTool`, and write the command with the literal `<mimir-lite-root>` path instead of `$HOME`.

### Changed

- README: the GeneXus versions table records the full agent runs on GeneXus 15, 17, and X Evolution 3 samples; the limits note that an attribute's uses are not indexed (only structural relations); the agent steps and the workflow table mention a workspace set up from the XPZ alone.
- The README agent steps and the install workflow handle an existing clone: when `<mimir-lite-root>` already exists, the agent inspects it read-only (`status`, current commit, `origin` URL), tells the user, and asks before updating; with a yes it fetches and updates by fast-forward only. When a fast-forward is not possible (unrelated history, local commits, or uncommitted changes), it stops, explains why, and offers a fresh clone into a new approved path; the old clone is never reset, deleted, or overwritten, and is removed or renamed only after an explicit yes and with a clean `git status`. Any clone, fetch, pull, or reset of the skill checkout needs the user's explicit yes first.
- The existing-clone check in the README agent steps and the install workflow, from a fifth end-to-end run: before the update question, the agent tells the user in one short message whether the clone is clean, its current commit, and whether `origin` is the README's URL; it runs each inspection and update command as a call of its own (no `&&`, `;`, pipes, or `cd`), so each matches a simple permission rule; after updating, it re-reads the workflow files already read in the session (at least `install.md`) before continuing; and when the user declines the update, it takes the commands from that clone's own `README.md` and `install.md`, since an older clone may lack newer options such as `-OnlyTool`. In the linking question, a "no new links" choice excludes every other choice.
- When the user asks to install or update the skill following the README, the `SKILL.md` workflow table and the install workflow tell the agent to read the README from its URL first, even when the skill is already installed or linked, and to follow its steps from the existing-clone check to the install audit.
- A new core rule in `SKILL.md`: during work on a KB workspace, nothing is saved to a memory tool outside the workspace without first asking the user, naming what and where, whatever the content (KB or workspace details, notes about the skill or its scripts, or anything else), even when other instructions ask for proactive saving. Setup step 14 and the setup completion checklist now point to that rule instead of repeating it.
- The find workflow opens with a first-question checklist: the once-per-session notice (when the session was not started in the KB workspace folder, say that permission prompts will continue here and offer to reopen in that folder) and the literal command form, both applied from the first question. `SKILL.md` "Running scripts" now also says one script call per command, with no pipes or compound commands, and that the agent reads the output in its own reasoning.
- When a property is absent from the export, the operational rules and the find workflow tell the agent to say the export does not carry it and to name no candidate value, not even as a default, a hypothesis, or what it "typically" is.
- The KB index reference states that `is_generated_object` marks pattern-instance output only and says nothing about authorship: objects with `0` may still be generated by GeneXus (Tables derived from Transactions, core modules, SDTs that support a pattern).
- The README agent steps offer the optional `mimir-delegate` skill as a choice in the linking question and never decide it for the user.
- Setup step 20a and the scaffolder step state that the scaffolder is a direct shared-script call that runs once before the shared-scripts allow rule by design (it creates the workspace whose settings hold the rule), and tell the agent to warn the user beforehand that the tool may ask permission for that one call.
- The setup closing (step 31 and the completion checklist) no longer says the scripts run without prompts when the session was opened outside the KB workspace: it then says that permission prompts continue in this session and that the allow rules apply once the agent tool is reopened in the KB workspace folder; only a session opened in that folder hears that the scripts now run without prompts.
- `SKILL.md` "Running scripts" tells the agent to read the skill's own workflow and reference files with the agent tool's file-read tool, not shell commands, and once per session, re-reading a file only when it changed (for example after a clone update).
- The find workflow gets the local time only when a reply or an operational record states a time, instead of before every reply, and still never reuses a previous timestamp or interleaves `Get-Date` between the gate's steps. When it suggests which objects likely hold the unlisted uses of an attribute, it labels that a hypothesis and points at pattern instances (`WorkWithForWeb`, `WorkWith`) and authored code objects, never at objects generated from those instances.
- Setup step 7b checks exactly the listed global instruction files, one existence check per path, and never searches or lists the whole user profile to find them.
- The setup-workflow changes above, including the setup closing and the exact global instruction files, and the runtime-gate fix below alter the setup contract: existing workspaces see a setup-contract change and re-audit once.

### Fixed

- The install audit (`Test-MimirSkillsRegistration.ps1`) accepts a comma-separated list in `-SkipTool` and `-SkipSkill` when run with `pwsh -File`, where `-SkipTool Codex,OpenCode` arrives as one string and used to stop with `BLOCK: unknown -SkipTool name 'Codex,OpenCode'`. Every value is split on commas (trimmed, empties dropped), so in-process arrays and comma lists give the same result; an unknown name inside a list still stops with `BLOCK:`, exit `1`, and nothing on stdout. The install workflow and the README agent steps show the comma-list form.
- Reverse-relation coverage is target-aware: for an `Attribute` target, `who-uses`, `impact-basic`, `functional-trace-basic`, and `object-info` used to report `coverage.complete=true` on a KB without mobile or GXflow types, although the index holds only structural relations to attributes (Transaction levels, Table keys and indexes) and no attribute uses from grids, filters, code, rules, or formulas. Coverage now adds `scope` (`calls`, or `attribute_references` for an `Attribute` target); with `attribute_references` it lists every indexed type whose attribute uses are not extracted (for example `WorkWithForWeb`, `Procedure`, `WebPanel`) with its count, and the `text` line says that only structural relations are indexed. The scope is chosen ignoring the case of `--object-type`, so a lowercase `attribute` target (which matches no relation rows, since object types match case-sensitively) still discloses the gap instead of reporting complete call coverage. Other targets keep the same list and gain only `scope: "calls"`. Exit codes and the index schema are unchanged; no rebuild is needed.
- The PowerShell runtime gate (`Test-MimirPowerShellRuntime.ps1`) accepts a prerelease `pwsh`: a version such as `7.6.0-preview.5` or `7.5.0-rc.1` used to block with `could not determine pwsh version`. The gate now compares the numeric part before `-` and ignores build metadata after `+`; as in semantic versioning, a prerelease of exactly the minimum (for example `7.4.0-preview.1` against 7.4, or `7.4.6-rc.1` against the 7.4.6 floor on Linux and macOS) does not meet it and blocks with the usual "or later required" message, while a prerelease of a higher version passes. The reported version keeps its suffix. A version whose numeric part is not a version still blocks as before.

## [0.3.0] - 2026-10-09

### Added

- Five object types in the catalog, so KBs that hold them sync and index instead of stopping on an unknown type: `OfflineDatabase` (mobile Offline Database), `ThemeTransformation`, and the GXflow types `BusinessProcessDiagram`, `WorkflowRole`, and `WorkflowDocument`. Each GUID comes from the XPZ Dependencies block of a public GeneXus sample. All five are `queryableByKbIntelligence=false`: inventory and `object-info` work, semantic queries on them return the `QUERY_NOT_SEMANTIC_FOR_TYPE` block.
- A sync or pre-scan blocked on an unknown object type now names each type: `<type GUID> type="<type name>" package="<package>" [<count>] names=...`, with the name and package read from the package's own `Dependencies` block (`unknown` when absent). The inventory adds `unknownTypesMessage` and per-type `typeName`/`typePackageName`; the sync wrapper template prints that message instead of a generic "Pre-scan blocked" line. Exit codes are unchanged.
- The install audit (`Test-MimirSkillsRegistration.ps1`) takes `-SkipTool` and `-SkipSkill` for the tools and skills the user chose not to link: where a link would be missing or covered by compatibility, it reports the new status `skipped_by_choice`, which is not a gap, so `overall` is no longer `REGISTRATION_GAPS` because of a declared choice alone. An existing link keeps its status (a broken one is still a gap), and an unknown name stops with `BLOCK:` on stderr, exit `1`, and nothing on stdout (the script help now lists its exit codes). The JSON adds `skippedByChoice` (`tools`, `skills`), `tools[].skippedByChoice`, and `summary.skippedByChoice`. The README agent steps and the install workflow pass `-SkipSkill mimir-delegate` when the user did not want delegation.
- An XPZ-only KB workspace, for users with no native KB folder: the setup workflow has an XPZ-only branch, and the scaffolder takes `-XpzOnly` (not combinable with `-KbNativePath`). The workspace `README.md` and `AGENTS.md` then say that no native KB folder is recorded and that the KB identity comes from the XPZ `Source` block written by the first sync; the stable identity is reported pending on that sync. The identity wrapper template reports `NATIVE_KB_NOT_RECORDED` (exit `3`) and changes nothing when no native KB folder is recorded, instead of failing on the placeholder path. The workspace templates no longer claim that the native KB folder "existed and was accessible": the scaffolder writes the result of its own check. Part of the same setup-contract change: existing workspaces re-audit once.

### Changed

- Reverse-relation answers (`who-uses`, `impact-basic`, `functional-trace-basic`, and the `incoming_relations` count of `object-info`) now carry a `coverage` object: `complete`, and the object types in the index whose calls are not extracted (`Panel`, `SmartDevicesApplication`, `WorkPanel`, `WorkWith`) with their counts. The `text` format adds one `coverage: incomplete` line when coverage is incomplete. Exit codes and the index schema are unchanged; no rebuild is needed.
- The coverage of reverse-relation answers also counts `OfflineDatabase` (events) and `BusinessProcessDiagram` (GXflow task bindings and conditions): their references to other objects are not extracted either. The rule now covers code or bindings that reference other objects, not only events or a `Source` part, and the find workflow points to the single list in the KB index reference instead of repeating it.
- The find workflow tells the agent to relay a partial-coverage answer to the user in plain words and never to present it as "no callers".
- The README "GeneXus versions" table now lists GeneXus X Evolution 2 and 3 and GeneXus 15 to 17 as tested with public samples, and states the known limit: calls from mobile objects (panels, their Work With, the Offline Database) and from GXflow business process diagrams are not indexed, and reverse-relation answers say so.
- The README agent steps ("Use it with an AI agent", "For the agent") now ask before linking, naming each link path and its target, and say that a request to install the skill is not consent to create links; after linking they run the install audit and relay its result; and they note that some tools load a newly linked skill without a new session. The install workflow's first-install rules say the same.
- The setup workflow starts with a completion checklist: read the whole file (in parts when the tool truncates it), and confirm the runtime gate and setup audit, the allow rules, the global instruction check, the `## Index triage` section, the setup-audit timestamp, and the closing message before declaring any completion state. A write to a global instruction file is now its own question, never bundled with other approvals, showing the file path and the exact block; the block names the `mimir-lite` skill instead of "this skill". The allow rules come first after the scaffolder, so the shared-scripts rule is offered before the first direct call to a shared script (the catalog reminder, the sync pre-scan), and the closing message tells the user to start the agent tool in the KB workspace folder, where those rules apply. ## [0.1.0] - 2026-10-05

First public release.

Mimir Lite is an agent skill that reads and understands a GeneXus Knowledge Base (KB) from its XPZ/XML exports. It never generates, builds, or imports GeneXus objects.

### Added

- `skills/mimir-lite/`: the core skill. A single router `SKILL.md` sends the agent to six workflows:
  - **setup**: creates a KB workspace next to a KB in one command with the `New-MimirKbWorkspace.ps1` scaffolder (folder layout, prefixed local wrappers, `README.md`, `AGENTS.md`, KB source metadata), and audits an existing workspace.
  - **sync**: materializes an XPZ export into an XML corpus, one file per object.
  - **find**: queries a derived SQLite index (`who-uses`, `what-uses`, `impact-basic`, and related queries) behind a mandatory freshness gate; the XML corpus stays the normative source.
  - **read**: structurally classifies a single object's XML (type, family, parts, risk).
  - **docs**: generates Markdown documentation from the XML corpus.
  - **install**: registers the skills in the agent tools on the machine (Codex, Claude Code, Cursor, OpenCode, Antigravity, or any tool that reads `SKILL.md` from a skills directory) and audits stale registrations.
- Agent onboarding: the README explains how to hand an agent the repository URL and an XPZ (a copy-paste prompt for the user and the install steps for the agent, including the skills folders each tool reads), and every script invocation uses one shell-neutral form, `pwsh -NoProfile -File "<absolute path>"`, so it runs the same from bash, PowerShell, or cmd.
- `skills/mimir-lite/references/`: an agent-facing knowledge base of object families, sanitized structural templates, operational rules, risk by object type, and the KB index methodology and reference.
- `skills/mimir-delegate/`: an optional skill for delegation to other LLM CLIs and for peer review by a panel of models, behind a confidentiality gate.
- `tests/`: a single test runner (`tests/Invoke-Tests.ps1`) with self-tests for the scripts, and a synthetic sample KB fixture (`tests/fixtures/sample-kb/`) that needs no real KB.
- `tools/`: contributor checks for text encoding (UTF-8 without BOM, LF), PowerShell and Python parsing, Markdown links and fences, script inventory, code language, and a mechanical pre-push check.
- Human documentation: English and Spanish `README`, `CONTRIBUTING`, `SECURITY`, and `CODE_OF_CONDUCT`; decision records under `docs/adr/` (scope and non-goals, packaging, language, license); the maintainer pre-push and peer-review methods under `docs/process/`; the translation policy and glossary under `docs/i18n/`; and the curated ideas backlog and discarded ideas under `docs/ideas/`.
- A GitHub Actions workflow that runs the test suite and the checks on `windows-latest`.

### Notes

- Licensed under the MIT License ([`LICENSE.md`](LICENSE.md)); the authors are listed in [`AUTHORS.md`](AUTHORS.md).
- Requirements: Windows, PowerShell 7.4+, and Python 3.8+ using only the standard library (including `sqlite3`). No GeneXus IDE, MSBuild, or GeneXus build tooling is needed.
- Windows only: the PowerShell layer relies on Windows paths, junctions, and the Microsoft Store Python stub detection. The Python engines use only the standard library and are portable in principle, but this has not been tested on another operating system. Known gaps on Linux and macOS: the scripts look for `python`, not `python3`; the registration audit requires `USERPROFILE`; the inventory and advanced-docs generators split paths on backslashes; and the Codex and OpenCode delegate adapters are Windows-specific.
- Out of scope by design: generating, cloning, or packaging GeneXus objects, building or importing XPZ into a KB, and MSBuild-based builds.
- `mimir-delegate` can send prompt content to external LLM CLIs. It is optional and gated; read [`SECURITY.md`](SECURITY.md) for what it sends and where the tools write state outside the repository.
- `mimir-delegate` keeps its machine-level state (detected capabilities, preferred reviewers, circuit-breaker state) under `%LOCALAPPDATA%\mimir-delegate`.
